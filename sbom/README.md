# Software bills of materials

IronMesh publishes CycloneDX 1.5+ JSON SBOMs for every container image and every source
component. Nothing in this directory is generated by hand; it documents where SBOMs come from
and how to verify them. `make sbom` produces the source SBOMs locally into `dist/sbom/`.

## What is generated, and by which tool

| Scope | Tool | Command (as run by `.github/workflows/release.yml`) | File |
|---|---|---|---|
| Container images (`ironmesh-pki`, `-policy`, `-bridge`, `-registry`, `-ota`, `-anomaly`, `-console`, `-fleet`) | syft (`anchore/sbom-action`) | SBOM of the pushed multi-arch image by digest, `format: cyclonedx-json` | `sbom-image-<name>.cdx.json` |
| Go services (`services/pki`, `services/policy`, `services/bridge`) | `cyclonedx-gomod` | `cyclonedx-gomod mod -licenses -json -output <svc>.cdx.json services/<svc>` | `pki.cdx.json`, `policy.cdx.json`, `bridge.cdx.json` |
| Python services and the wire library | `cyclonedx-py` (`cyclonedx-bom`) | `cyclonedx-py environment --of JSON -o <svc>.cdx.json <venv>/bin/python` on a clean venv with only the component installed | `registry.cdx.json`, `ota.cdx.json`, `anomaly.cdx.json`, `ironmesh-wire.cdx.json` |
| Rust agent / fleet simulator and the ESP32 host crates (firmware) | `cargo cyclonedx` | `cargo cyclonedx --format json --all-features` in `device/agent-rs`, `cargo cyclonedx --format json` in `device/esp32/host` | `ironmesh-agent.cdx.json`, `im-*.cdx.json` |
| Console | `@cyclonedx/cyclonedx-npm` | `npx @cyclonedx/cyclonedx-npm --omit dev --output-format JSON` in `console/` | `console.cdx.json` |

The ESP32 firmware image itself is built from ESP-IDF v5.3.2 plus the managed components in
`device/esp32/main/idf_component.yml`; its SBOM is the `cargo cyclonedx` output of the host
crates (the shared C protocol core) together with the pinned IDF version recorded in the
release notes. ESP-IDF's own `esp-idf-sbom` tool can additionally produce an SPDX SBOM of the
linked image (`esp-idf-sbom create build-prod/project_description.json`); it is not part of the
pipeline yet.

## Where SBOMs are published

* **Image SBOMs as signed attestations.** Every image is attested with
  `cosign attest --type cyclonedx` (keyless, GitHub OIDC). The attestation is stored next to the
  image in `ghcr.io/lumidren/ironmesh-<name>` and is verified before every deployment
  (`scripts/ci/deploy_helm.sh verify-images`).
* **GitHub Release assets.** For tags `v*` every SBOM above is attached to the GitHub Release,
  listed in `SHA256SUMS` and covered by the SLSA v1 provenance produced by
  `slsa-framework/slsa-github-generator` (`*.intoto.jsonl` on the release).
* **Workflow artifacts.** Pushes to `main` keep the image SBOMs and source SBOMs as workflow
  artifacts (`image-<name>`, `source-sboms`) for 30 days.

## Verifying

```bash
# Image signature and SBOM attestation (keyless identity = this repository's release workflow)
IMAGE=ghcr.io/lumidren/ironmesh-pki:0.2.0
cosign verify "$IMAGE" \
  --certificate-identity-regexp '^https://github.com/lumidren/IoT-Security-Framework/.github/workflows/release.yml@' \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com
cosign verify-attestation --type cyclonedx "$IMAGE" \
  --certificate-identity-regexp '^https://github.com/lumidren/IoT-Security-Framework/.github/workflows/release.yml@' \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com \
  | jq -r '.payload' | base64 -d | jq '.predicate.components | length'

# Release assets: checksums, then SLSA provenance
sha256sum -c SHA256SUMS
slsa-verifier verify-artifact console.cdx.json --provenance-path multiple.intoto.jsonl \
  --source-uri github.com/lumidren/IoT-Security-Framework --source-tag v0.2.0

# Firmware bundles are signed blobs as well
cosign verify-blob --bundle ironmesh-esp32-0.2.0.tar.gz.sigstore.json ironmesh-esp32-0.2.0.tar.gz \
  --certificate-identity-regexp '^https://github.com/lumidren/IoT-Security-Framework/.github/workflows/release.yml@' \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com
```

## Vulnerability gating

SBOMs are inputs, not gates. The gates are Trivy on every image before it is signed
(`release.yml`, HIGH/CRITICAL with a fix available fails, exceptions only via `.trivyignore`
with an expiry), and the dependency audits in `security.yml` (Trivy fs, cargo-audit, cargo-deny,
`npm audit --audit-level=high`, OSV-Scanner report).
